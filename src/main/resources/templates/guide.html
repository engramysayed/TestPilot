Keel turns stories, knowledge packs, and spreadsheets into live browser evidence, visual proofs, scheduled suites, and downloadable automation code.

Prerequisite

Create a project, set the website URL under Settings, add a login account when cases need sign-in, and (optional) preferred how-we-find-it attributes (locators) such as data-axis-test-id. Features live in the sidebar: Generate, From knowledge, Plain cases, Record, Suites, Execute, Automate, Bug Hunter, and more.

New

What's new (9 Nov 2026)

The latest changes, with links to the section that explains each one.

  • Alerts also reach project members. A suite failure now goes to every project member who turned on alerts in Account, using the email or Telegram chat id they saved — no shared server list needed.
  • Email is the first supported channel. Admins set Gmail SMTP once (KEEL_MAIL_* env vars with a Gmail app password); users just type their own address. Slack was removed; Telegram stays but ships off by default.
  • Sidebar regrouped. Items now sit under Author tests, Run, Review and Workspace, with clearer names (Generate with AI, Convert to code, Record browser). Screenshot diffs stays inside Execute; Runtime packages is a project tab.
  • Humans instead of ids. The Runs page and the dashboard now label runs by when they happened (Nov 09 · 16:42) and show the project name — the raw exec_… id is still on hover.
  • Delete any run. Every row on Runs & evidence has a Delete button that removes the run and its evidence folder. Active runs refuse to delete — cancel first.
  • English-only UI (for now). The Arabic toggle was dropped because it pulled Arabic date pickers in from the OS locale. The portal is pinned to English.
  • Engine picks up schedules. GET /api/schedules/due now accepts a runner bearer token, so the engine no longer floods its window with HTTP 401.
  • Suite tags, explained. On Suites: Smoke is the quick must-pass set, Regression is the full what-broke set, Nightly is the overnight run.
  • Bug Hunter triage reads the right key. A field-name mismatch meant the Review findings panel showed zero even when the hunt had bugs; fixed.
  • Test ids come first. Every stage now uses one locator order: your preferred hook, then data-testid, then a unique id or name, then role and label, then visible text. See Locators & languages.
  • Refunds. When a charged run fails because of the platform, a refund request reaches the account owner automatically. See Refunds.
  • Runs recover on their own. If a worker crashes or hangs, the run is picked up again (or marked for review) within about a minute, without restarting Keel.
  • Run on a real phone. Project → Mobile → Run on a phone. See Mobile.
01

Generate

On Write test cases, describe visitor behavior or paste stories. Keel drafts cases, runs a quality gate, then you import into the project library.

structured intake
As a…shopper
I want…to pay with a saved card
So that…checkout finishes quickly
AcceptanceOrder confirmation shows an order number
  1. Open Write test cases and pick your project.
  2. Fill the story title, acceptance criteria, role, and surface. Free-text, the AI model, compare, bulk upload, and paste-from-another-AI are already open on the page.
  3. Generate. Review the quality-gate panel before you import.
  4. If the gate failed, fix issues or explicitly confirm import — Keel refuses silent import when checks have not passed.
  5. Use the suggested how-to-test (Keel path) tip when shown — it is guidance, not a second product.
  6. Story coverage. Every generated case is tagged with the story it covers (req:US-1, req:AC-2). Open Story coverage on Generate to see which stories have cases and which have none. Suites can filter by the same tag.
  7. Language. Paste Arabic stories to get Arabic cases. Button names and messages are quoted exactly as written, in the app's own language.
Tip

You can also paste CSV/JSON from an external AI under Import into project, or upload a spreadsheet on the project’s Test cases tab.

Credits

Classic Generate uses the Generate credit price (one writing job). See Pricing.

01b

Generate from knowledge

On From knowledge, you pick knowledge packs on the project and Keel drafts cases from that material. This is separate from classic Generate (stories and free text).

  1. Open From knowledge and choose your project.
  2. Select one or more knowledge packs, set a batch size, then start the run.
  3. Review the drafted cases, then import into the library when you are ready.
Credits

Usually billed under Generate credits (same writing family). If Admin → Prices shows a separate GFK row, that row is Owner-editable on Admin → Prices like other credit services.

01c

Plain-English cases

On Plain cases, write steps in everyday English. Keel helps turn them into library cases you can run and automate.

  1. Open Plain cases, pick the project, and describe what the visitor does.
  2. Review the proposed cases, then save them into the project library.
  3. Run them from Execute or fold them into a suite.
Credits

Writing stays under Generate credits when billed as a writing job. Running those cases later uses Execute credits.

02

Record and automate

On Record you do the test yourself in Chrome. Keel writes the steps, remembers the buttons, and can write the automation code from that. Chrome does not open a second time for the code.

You get two things

A written test case in the project, and — if you leave Build on — the same kind of code package Automate makes.

  1. Create a project and set its website. Record opens that address.
  2. Open Record. Pick the project. Give the test a short name, such as “Pay with a saved card”. Press Next.
  3. Leave sign-in on “No sign-in needed” unless a later run must log in first. Press Next.
  4. Press Start recording. Chrome opens on this computer. Click and type the way a visitor would. The step list on the Record page grows as you go.
  5. Use the Keel bar at the bottom of that Chrome window when you want a check:
    • Steps — back to normal. Clicks and typing are recorded.
    • Check this — then click the heading or message that must be on the page, such as “Order confirmed”.
    • This page — confirm the address you landed on.
  6. Press Stop. Read the steps. The card tells you how many buttons were remembered and how many checks you added.
  7. Leave Build the framework from this recording checked when that card has something to build. Leave Run it once off. Run it once is an Execute run: Keel opens the site again and finds the buttons from the written steps. It does not reuse the locators from the recording. Cursor is involved only when that project’s authoring engine is Precision.
  8. Press Save test. The case is the next TC_ number in the project. If the build starts, open Watch the framework build. When it finishes, download the ZIP from Code packages.
A short example

Open the shop, click Pay, press Check this and click “Payment received”, then press This page. Stop, keep Build checked, and save. You get the written steps and a Java test for that page.

Credits

Building the code charges the framework price once for this test case. Running it once charges the run price once for this test case. If the account cannot cover that, the written test is still saved and the job is not started.

  • Password. If the site asks you to sign in, type the password yourself. Keel does not store it. Choosing “Yes” on sign-in only adds a note that the later run should use a project login account.
  • A button with no stable name stays in the written test only. It is left out of the code. Checks on text and on the page address still go into the code.
  • Same website only. Another address has to be on the project’s website.
  • Web only. A mobile-app project cannot be recorded.
  • One recording at a time, for at most 20 minutes. You can still save the steps you have.
03

Quality gate

Before cases land in your library, Keel shows a structured panel. Fix blocking issues; treat coverage warnings as informational.

quality checks

Fix these before importing

  • errors — rule / field / message / severity
  • suggestions — optional improvements
  • failures[].howToFix — concrete repair text
  • coverageWarnings — warn-only; do not block alone

Import asks you to confirm when passed === false.

  • Blocking — gate failures and errors. Read how to fix and revise stories or steps.
  • Warn-only — coverage warnings are informational; they do not fail the gate by themselves.
  • Import confirm — when the gate has not passed, Import stays gated until you confirm.
  • Keel path — a suggested how-to-test label may appear alongside the panel.
04

Execute

On Run tests, Keel runs cases in a real browser. You can review the selected cases first; Accept saves them to the library, then the run starts. Every step can produce a screenshot. Open Run history and Evidence for results.

Prepare

Project ready

Website URL, login accounts, and test cases imported or uploaded.

Run

Start execute

Pick the project (and device when mobile is enabled). Watch status from the sidebar chip.

Review

Results & evidence

Pass/fail per case. Open Evidence for step screenshots and results.

  1. Open Run tests, pick the project, and select the cases (or upload a workbook).
  2. Optional: check Review cases before run (Cursor or Keel). More than 5 selected cases split into batches (Owner sets the size on Admin → LLM & API keys; default 50). Inspect the combined proposed cases after the last batch. Filler words such as list, area, and visible stay outside quotes — leftover Expected becomes 'Upload Transactions', not 'Upload Transactions list area'. The live heading (for example 'Upload Transactions List') is applied later during the run when that heading is unique on screen.
  3. Accept & run saves those cases into the project library, then starts the run. Uncheck review to run the library as-is. Review is not charged; the run price still applies when the run starts.
  4. Quoted clicks use on-screen names. When a click lands on a menu row, Keel uses an inner preferred hook from project Settings if that hook is unique in the page. If the row is unique but the hook was cloned elsewhere (open submenu), it still clicks that inner hook under the row. Otherwise it keeps the row xpath.
  5. Excel verbs Keel does not already treat as click / type / check are skipped unless the Owner adds them on Admin → LLM & API keys (Authoring verbs). Built-in words stay read-only. Default: observe is treated as assert.
Prerequisite

For web runs, the target site must be reachable from the Keel runner. For mobile, see Mobile (Appium + device).

Credits

Execute charges Execute credits once per test case in the run. Review-before-run is not charged. Heal Accept/Reject and flaky tags live on Evidence after the run.

04b

Evidence

After a run, open Evidence from Run tests, Run history, or the Evidence page. You see step screenshots, pass/fail, and heal suggestions.

  • Heal Accept / Reject — when Keel finds a new way to reach a control, Accept keeps that fix for later runs; Reject leaves the case as-is.
  • Flaky tags — cases that sometimes pass and sometimes fail get a clear flaky mark so you can decide what to fix next.
  • Evidence is the review surface for runs — it does not start a new charge by itself; the run already used Execute credits.
Credits

Heal review is part of Execute for day-to-day use. Admin → Prices may also list a confirmed HEAL_REVIEW credit row — Owner-editable like other services.

04c

Visual diffs

Prove and compare screens after a run. On Run tests, open the Visual diffs panel to see baseline, actual, and diff side by side, then Approve baseline when the new look is correct. This is different from the authoring Visual check wording in a spreadsheet.

  1. Run cases that include a visual check.
  2. On Execute (or via Evidence), open pending visual diffs for the project.
  3. Compare Baseline | Actual | Diff. Approve when the screen should become the new baseline, or replace the baseline image if needed.
Credits

Visual compare work usually sits with the Execute run. Pricing may also list a confirmed VISUAL_DIFF credit row — Owner-editable on Admin → Prices.

04d

Suites

On Suites, group cases into test packs. Add tags (smoke, regression, nightly, or your own), attach a schedule, pick an alert channel, and promote a green pack to an always-on monitor.

  • Tags — label a pack so you can find and filter it later.
  • Schedule — cron (e.g. 0 2 * * *) or an interval, at most every 5 minutes. Choose the time zone (default Africa/Cairo) and the login profile scheduled runs use.
  • One run at a time — if the previous scheduled run is still going, the next slot is skipped and shown as SKIPPED_OVERLAP. If Keel was down for more than an hour past a slot, that slot is skipped (MISSED) instead of running at an odd time.
  • Running a pack by hand does not move its schedule.
  • Alerts — email or Telegram: any failing case alerts (all failed = critical, some failed = warning), and so does a run that crashed or could not start (no credits, no test cases, no workbook).
  • Promote to monitor — keep a green pack watching prod or staging. The pack shows its last status (green / degraded / red) and when it was checked.
Credits

Manual or scheduled suite runs use Execute credits per case. Pricing may also list a confirmed SUITES_MONITOR row for monitor/schedule add-on credits — Owner-editable on Admin → Prices.

05

Automate

On Build code, upload or select a workbook. Keel opens the site, checks the steps work, then builds a framework you can download. If you already clicked through the site on Record, use Build the framework there instead. That uses the same builder and does not open Chrome again.

  1. Open Build code and choose the project.
  2. Provide the test-case workbook (or use cases already on the project).
  3. Optional: the same Review cases before run as Execute — leftover Expected quotes, then Accept & run saves the library and starts the framework job. Step verbs follow the same Authoring verbs list as Execute.
  4. Start conversion. Watch progress on Status / the sidebar job chip.
  5. When finished, download from Code packages.
Tip

Author clear Steps and ExpectedResult first (see Case authoring). Vague steps produce weaker automation.

Stronger builds

Packages now keep several ways to find each control, prefer clear on-screen names when they are unique, and remember plain-language finds you already accepted. That means fewer brittle clicks when the page layout shifts a little.

Credits

Automate charges Automate credits once per test case in the build (not once for the ZIP).

New

Locators & languages

How Keel chooses the way it finds each element, and how to keep tests working when the site changes wording or language.

1–2

Your hook, then test id

Attributes developers add for tests, such as data-axis-test-id or data-testid. They survive redesigns and translations.

3–4

Unique id or name

Only when a developer wrote it. Ids made up by a framework (ember123, ctl00$…) are never used as the main locator.

5–7

Role, label, text

Button name, placeholder, visible words. Easy to read, but they change when the copy or the language changes, so they are kept as fallbacks.

  • Locator ranking (Projects → Settings): Stable first uses the order above. User-facing first puts role and label before test ids, if your team prefers tests that read like the page. Your preferred hook is first in both.
  • When a test id exists on the element, it becomes the main locator even if the step was proven on a label.
  • Generated pages keep up to two fallbacks per element. During a customer run, the first one that matches wins, and the run log says when a fallback was used.
  • Arabic and English. Steps can be in either language. Keel understands Arabic verbs (اضغط، انقر، أدخل، اكتب، اختر، تحقق، مرر، اسحب) and ignores spelling differences such as أ / إ / ا and ة / ه.
Best practice for Arabic/English apps

Ask your developers to add one test id to every button, link, and field. It is the only locator that keeps working when users switch language.

06

Framework export / packages

Code packages lists automation ZIPs Keel built. Download the framework when Automate finishes, or when a Record build finishes. Builds include multi-way finds, smarter name matching, and remembered plain-language locators so heal and reruns stay steadier.

  • Packages are per project / conversion job — open Code packages after Build code succeeds.
  • Use the downloaded ZIP in your own CI or IDE; Keel does not push to your repos automatically.
  • No extra credit line for these build quality improvements — they ship inside Automate.
07

Bug Hunt / triage

On Bug Hunter, Keel explores the site and produces a report. Nothing is added to your test library automatically.

CONFIRMED ≠ promote

Marking a finding Confirmed is triage only. Cases enter your library only when you explicitly promote (Add to test cases) after duplicate checks. Automation ready stays false until you promote.

  1. Start a hunt for the project. Download the report when ready.
  2. Open Review findings (when triage is enabled). Decide each bug.
  3. Confirm real bugs; dismiss noise. Confirm does not merge into the library.
  4. For confirmed items you want as cases, use the separate promote / Add to test cases flow.

New

Refunds

Credits charged for a run that failed can be returned. The account owner decides.

Automatic

Platform failure

The browser crashed, the network dropped, a worker stopped, or the AI provider was down. A request opens within about two minutes.

You

Request refund

On a failed run's page, add a short note and press Request refund. The page then shows the request status and the owner's reply.

Owner

Admin → Refunds

See who, which project and run, what was charged, why it failed, the run timeline, and links to evidence. Refund all or part, or reject with a reason.

  • Failures caused by the test itself (a wrong step, a wrong expected result) or by setup (wrong password, wrong URL) are not opened automatically, but you can still ask.
  • A run is refunded at most once, and never more than it was charged.
New

Private app tunnel

Run cloud tests against a site that only exists on your computer or VPN.

  1. Your admin turns the tunnel on and gives it its own web address (for example tunnel.your-keel.com), separate from the Keel address.
  2. On your computer run keel tunnel start --project <id> --target http://localhost:3000.
  3. The Execute page shows Tunnel: active. Runs for that project use the tunnel instead of the project URL.
  4. Restarting the command keeps the same address. Add --re-enroll to get a new one.
If the command stops

After about a minute the badge shows offline and runs go back to the project URL.

09

Roles / approve signup

Admins approve access requests and assign a role. Built-in roles include Owner, Admin, and Member; owners can define custom roles with permission codes.

  1. Visitor submits Request access with a work email.
  2. Admin opens Administration, reviews pending users, and approves with an explicit role (no silent default).
  3. Set credits separately after payment — approval alone does not grant credits.
  4. Custom roles pick permissions from one multi-select list, the same kind of list used to pick test cases on Execute.
Prerequisite

Pending or locked accounts cannot start jobs. Approve first, then grant credits.

10

Account

On Account, the vision choice and the alerts are two different settings.

  • Vision model is only the model that looks at the screen during a run (UI-TARS, or Qwen vision). It stays in this browser. It does not write test cases. Writing uses Gemma, chosen on Generate.
  • Alerts are saved on the account. Keel sends a message when a run fails or finishes with a block. Turning a channel on sends a confirmation first, and the setting is kept only if that message goes out.
  • Telegram and email send only after this Keel computer has a bot token or a mail server configured.
  • A project’s Usage and budget is a cap on that project. It is not the same as the account credit balance in the top bar.
  • The account owner sets install-wide LLM keys, review batch size, browser, and Authoring verbs on Admin → LLM & API keys. Members cannot change that page.
11

Mobile

When mobile is enabled for a project, configure the app and a device under Project Settings. Appium must be available to the runner.

  • Appium — required. Without a working Appium server, mobile Execute/Hunt cannot drive the device.
  • Emulator — Android virtual device registered with Keel.
  • USB / UDID — real phone with USB debugging authorized; unlock debugging when the device shows “not authorized”.
  • App file (APK) — upload and inspect; pick the launcher activity when the APK exposes more than one.
  • Already installed — use the package already on the phone instead of uploading an APK.

Run on a phone

  1. On the computer the phone is plugged into, enroll a runner (Project → Settings → Private runners), set KEEL_RUNNER_TOKEN, and start scripts\mobile-runner.cmd.
  2. Project → Mobile → Find connected phones, pick the phone, optionally list test case IDs, then Run on phone.
  3. Keel reserves the phone, starts Appium, and waits for the runner. Results appear in the table case by case.
  4. When the run ends — or if the runner stops responding for about 45 seconds, or nobody picks the run up in 5 minutes — Keel stops Appium and frees the phone. A phone that was left stuck is freed within a couple of minutes.

Writing steps

One clear action per line. Name the control and the action from the live UI.

Avoid

Vague shorthand

  1. Login
  2. Add item
  3. Check
Prefer

Exact actions

  1. Open the Login Page at /login
  2. Enter the username
  3. Enter the password
  4. Click the Login button

03

Verbs Keel understands

A step runs when Keel classifies its verb as click, type, select, clear, check, skip, drag, hover, double-click, or right-click. Unknown verbs are skipped. The Owner can add extra words onto those kinds on Admin.

  • Click — click, press, tap, open, go to, add (as in “add the …”).
  • Type — enter, type, fill, input, select (line starts with select), choose, pick, leave/keep empty, leave blank, do not fill, skip the field.
  • Clear — clear the … field (empties the field). A Clear button is still Click.
  • Drag / drop — Drag the Ticket card onto the Done column (two named controls on the page).
  • Hover / double-click / right-click — hover over …, double click …, right click ….
  • Check visible — confirm, verify, shown, visible, see, displays, is shown, are visible.
  • Skip the line — post-login…, do not … at the start of a step.
  • List rows: a click that names a shared cell (with Pending edit status or "Pending Edit") uses the first matching table/grid row. Quote a person name when you need that person: Click on "Sara Ali". Two Login buttons on a page (not in a grid) stay unresolved.
  • Arabic — Click: اضغط, انقر, افتح, اذهب إلى. Type: أدخل, اكتب, املأ. Select: اختر, حدد. Clear: امسح. Check visible: تحقق, تأكد, يظهر. Hover: مرر. Drag: اسحب. Login words: تسجيل الدخول, اسم المستخدم, كلمة المرور.
  • Login / password / “click the login button” stay in code. They are listed on Admin as code-only specials and cannot be remapped.
  1. The account owner opens Admin → LLM & API keys and the Authoring verbs block (same Owner-only page as review batch size and browser).
  2. Built-in words are a read-only table. Add an alias: one word (letters only, 3–40), then treat as Click, Type, Select, Clear, Check visible, Ignore, Drag, Drop, Hover, Double-click, or Right-click. Save. Max 50 aliases.
  3. The next Execute, Automate, Generate review, or Record bind uses the list. Save on a running portal does not need another restart.
Default

Install seeds observe → Check visible, so Observe the Agent User Details page is displayed waits for that page instead of skipping the line. The Owner may change or delete that alias. Built-in words such as tap cannot be remapped.

Not a status filter

A status such as Pending Edit selects the first matching list row (the flow, not a specific person). Quote a unique name when the person matters. Review only sees the workbook, so quote important names and asserts there too.

  • Blank TestData (or blank line) → Keel invents from the field identity (names, *@example.com, etc.).
06

Visual check

Optional. Describes what the screen should look like after the case’s steps pass.

  • Write a short claim in plain language (form visible, heading present, cart still shown).
  • The steps decide pass or fail; the screen check is an extra check on top.
  • Uncertain or very low-confidence visual answers alone do not fail a case that already passed its steps.
07

What each case must include

Everything Keel needs to run the case without guessing.

Context

Starting page, role, and whether login is required.

Exact actions

Named controls and verbs — not “do the thing”.

Distinct names

When two similar items exist, name both so nothing is swapped.

Observable outcomes

What the user should see or reach after each important step.

AI rewrite → CSV

Copy a ready prompt into any AI chat. The AI returns CSV with Keel's column headers. Paste it on Write test cases → Paste from external AI, or save it and upload it on your project's Test cases tab.

  1. Click Copy prompt.
  2. Paste into any AI chat (ChatGPT, Claude, Cursor, etc.).

  4. Copy the AI's CSV only into Excel (or save as .xlsx).
  5. Spot-check a few rows, then paste them on Write test cases (Import into project) or upload the file on your project's Test cases tab.

Large suites: repeat per batch and append rows in Excel. Do not paste the whole workbook at once.
