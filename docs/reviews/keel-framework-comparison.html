How the five frameworks can improve Keel

The practical answer: keep Keel’s durable locator memory, but stop treating slimmed HTML as the only source of truth.

The recommended Keel flow

Deterministic first. AI last.
Known user locators and saved locators must win. Accessibility and relational evidence fill gaps. Vision is a controlled fallback and must never override a valid preferred locator.
1 · User locatorCustomer-supplied locator always wins.
2 · Known-goodReuse a locator proven on this route and origin.
3 · AccessibilityBrowser-computed role, name, labels, and state.
4 · Preferred hooksdata-axis-test-id and configured attributes.
5 · RelationsInside dialog, below heading, near OTP field.
6 · Stable DOMExact text, ID, name, autocomplete, safe CSS.
7 · VisionOnly when semantic evidence cannot identify the control.

What each framework contributes

TesterArmy E2E

Accessibility tree plus optional screenshots

Strength: verified action replay without repeated model calls.

Borrow: cache actions only after a later assertion proves them; report stale replay reasons.

WebdriverIO

Browser accessibility tree, CSS, text, XPath, Appium

Strength: strict semantic selectors and mature protocol support.

Borrow: role/name locators as first-class types; reject zero or multiple matches.

Nightwatch

WebDriver plus Appium

Strength: one platform for web, mobile, component, API, visual, and accessibility testing.

Borrow: reusable page objects, commands, API setup, visual baselines, and reports.

Midscene.js

Screenshot-first visual understanding

Strength: icon-only controls, canvas, cross-origin frames, and visually complex UI.

Borrow: visual fallback and visual assertions, with explicit confidence and evidence.

Maestro

Accessibility tree plus state and relational selectors

Strength: readable, resilient mobile flows.

Borrow: selectors that combine ID, enabled state, and relationships such as below, inside, and childOf.

Why slimmed HTML misses controls

Identity is distributed

A control’s useful identity can come from descendant text, aria-labelledby, an associated label, a dialog, a row, a frame, or a shadow root. A serializer can remove the relationship that makes it understandable.

Some controls are visual

Canvas buttons, icon-only controls, and custom navigation may be clickable without a strong CSS or text candidate. Vision belongs here, but only after deterministic evidence is exhausted.

Valid does not mean safe

A selector that matches two buttons, a hidden first match, or a disabled control must be rejected. Keel should enforce zero / one / many matching rules and actionability checks.

What Keel should send to the model

Current control: role=button · accessibleName="Verify OTP" · visibleText="Verify OTP"

Preferred: data-axis-test-id=verify_OTP_Button

State: visible, enabled · frame=[] · shadow=[]

Relations: inside OTP form · near verification-code input

Candidates: preferred → role/name → text → relation → CSS → vision

Implementation sequence

1Add browser-computed role and accessible name.
2Preserve frame, shadow, form, row, and label relations.
3Store multiple locator forms and the successful one.
4Reject ambiguity and hidden/disabled matches.
5Add verified action replay with stale reasons.
6Call Cursor/Ollama/vision only after deterministic layers fail.
