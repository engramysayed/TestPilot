## 1. Bilingual (Arabic / English) apps — recommendation

**Problem.** Text-shaped locators (`aria-label`, placeholder, visible text, role + name) are copy. When the app switches
language, every one of them breaks at once.

**What Keel does now (Done).**
1. Stable-first ranking is the default, so a test id / human id / name is primary whenever one exists, and a copy-based
   locator is only a fallback.
2. A verified test id is promoted even when the proof ran on a label.
3. Arabic steps bind: Unicode tokens, Arabic normalization (أ/إ/آ→ا, ة→ه, ى→ي, tashkeel removed, ٠-٩→0-9), Arabic verbs
   classify (اضغط → click, أدخل → enter, تحقق → verify, …).

**What to do next.**

| Step | Why |
|------|-----|
| Ask the customer's developers for `data-testid` (or your hook, e.g. `data-axis-test-id`) on every interactive control. | The only locator that survives copy, layout *and* language. One attribute per control is enough. |
| Add a **locale matrix** to Execute: run the same suite with `?lang=ar` / `Accept-Language: ar` and `en`, and flag any step whose primary locator is `LABEL`/`TEXT`/`ROLE_NAME` (`LocatorStabilityPolicy.languageDependent`). | Finds copy-coupled locators before the customer does. |
| In the ZIP `locator-report.md`, list every copy-dependent primary per page (tier counts per page). | Customers see brittleness before running. |
| For text fallbacks, emit **both** languages when the proof saw both (`FirstOf.of(textEn, textAr)`). | Fallback survives the switch. |
| Generated test data and asserts: keep quoted UI text in the UI language of the run; let projects declare `uiLanguages: [ar, en]`. | Asserts on messages are inherently language-bound. |

## 2. Per-project ranking mode — how it works (Done)

- Stored in the site's `preferred-hooks.json` next to the hooks: `{"attributes": [...], "locatorMode": "stable-first"}`.
- UI: **Projects → Settings → Locator ranking** (`PATCH /api/projects/{id}` with `locatorMode`).
- Activated with the hooks for the whole job (`PreferredHooksStore.activate(hooks, mode)` in `ProvePhase`, `EmitPhase`,
  `LiveHuntService`), so bind, prove ranker, codegen ladder/bag and vision all read the same mode.

| Tier | stable-first (default) | user-facing-first |
|------|-----:|-----:|
| Preferred hook | 100 | 100 |
| Test id | 90 | 80 |
| Unique human id | 80 | 60 |
| Unique name | 75 | 55 |
| Role + accessible name | 65 | 90 |
| Label (aria-label / placeholder / title / alt / label anchor) | 60 | 85 |
| Visible text | 50 | 70 |
| Other attribute CSS / XPath | 40 / 35 | 40 / 35 |
| Positional | 10 | 10 |
| Generated id/class, absolute path | 0 | 0 |

## 5. Heal and visual select — assessment

**How it works today.** `HealCascade`: DOM shortlist pick (Ollama or Cursor, candidateId only) → optional vision widen
(UI-TARS / Qwen bbox → `elementFromPoint` → climb to interactive ancestor → match an existing candidate or build a new
validated locator) → last-hope invent (Cursor / AgentRouter) with intent-token check and LoopGuard budget → recovery plans.

| Finding | Status |
|---------|--------|
| New vision locator built id → test id; a generated id aborted grounding | **Done** (policy order, try next option) |
| JS generated-id detector duplicated in `SeleniumGroundingBrowser` drifted from Java (no ASP.NET/JSF) | **Done** (synced). Better: inject the shapes from Java at runtime so there is one source. |
| `vision-heal.md` asks for `Thought:` + `Action:` while `heal/pick.md` forbids prose | Recommend one JSON shape `{"candidateId","reason"}` for both and one parser. |
| `elementFromPoint` ignores shadow roots / iframes | See L-c. |
| bbox center can land on a decorative child; the climb picks the nearest interactive ancestor, which may be a large card | Score ancestors by area vs bbox area and prefer the smallest interactive one that contains ≥ 60 % of the bbox. |
| No confidence floor per model | Add `delivery.vision.min-confidence` per provider; below it, skip grounding instead of adding a candidate. |
| Heal decisions are not reused across TCs in one job | Cache intent→candidate for the job (same page route + same intent text) to save model calls. |

## 6. Test-case generation — assessment

> **Done (2026-11-07 evening):** prompts in catalog, `requirementRef`/`req:` traceability + Story coverage, language rules, example fixed. Remaining: dedupe across batches, technique checklist.

Generation prompts live in `src/main/resources/static/prompts/keel-tc-generate-*.txt` (JSON + CSV), plus the capability
manifest and testing techniques.

| Finding | Recommendation |
|---------|----------------|
| These prompts are **outside `PromptCatalog`**: not in Admin → Prompts, not versioned with `VERSION`, no override. | Move to `prompts/generate/*` and load via `PromptCatalog` (same as heal/vision). |
| No traceability field: a case cannot point back to the story / acceptance criterion it covers. | Add `requirementRef` (story id / AC number) to the JSON schema; show a coverage matrix (story × cases) on Generate. |
| English-only rules and examples; site-specific leakage ("News Feed", "home feed"). | Add a language rule: write steps and quoted UI text in the UI language of the requirements (Arabic stays Arabic); remove site-specific nouns. |
| The JSON example's last step ("Confirm a wrong-password or credentials error is visible") breaks its own rule (quote the exact message). | Fix the example. |
| No dedupe across batches. | Normalize title + steps and warn on near-duplicates before saving to the library. |
| Coverage is "happy / negative / boundary when implied". | Add an explicit technique checklist per field type (required, length, format, equivalence classes) driven by the capability manifest, and report which were applied in `coverageNotes`. |

## 8. Mobile — hidden bugs and gaps

> **Done (2026-11-07 evening):** lease heartbeat during runs, stuck-device maintenance, end-to-end run orchestrator + runner agent. Remaining: device acceptance (M6), Arabic normalization in `MatchNormalizer`, generated resource-id filter.

Mobile is behind `delivery.mobile.enabled=false`, and the code says no device acceptance run happened (M6). Before turning it on:

| Severity | Finding |
|----------|---------|
| **High** | `DeviceLeaseGuard.heartbeat` has **no production caller**, and lease expiry is **30 s** (`leaseExpirySeconds`). Any mobile run longer than 30 s after activation loses command permission. Wire a heartbeat (every `leaseHeartbeatSeconds`) into the Appium session loop — same pattern as `LeaseKeeper`. |
| **High** | `DeviceLeaseGuard.reconcile` has **no caller**. An abandoned RESERVED lease or an expired ACTIVE lease with a dead session keeps the device `BUSY` forever. Add a scheduled reconciler with `QuarantineProof` checks. |
| High | `MobilePortalStore.createLease` has no caller in the portal: there is no orchestrator that reserves → starts Appium (`SupervisedAppiumLifecycle`) → runs → releases. The pieces exist; the run pipeline does not. |
| Medium | `mobile-runner` `MatchNormalizer` only collapses whitespace: no case folding and no Arabic normalization, so `text=` binding misses on Arabic apps. Reuse `IntentText.normalize`. |
| Medium | Resource ids are ranked first (good) but R8-obfuscated / Compose-generated ids (`a0b`, `compose:123`) are not filtered — reuse a mobile variant of `GeneratedIdDetector`. |
| Low | Mobile lease host locks live in memory + file locks; after a crash, stale lock files need the reconciler above. |
